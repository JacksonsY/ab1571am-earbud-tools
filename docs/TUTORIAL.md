# 通用排查教程

## 1. 把现象拆成可以验证的问题

先选择一个目标，而不是直接寻找“一键开启所有功能”的命令。

| 现象 | 首先核查 | 修复后怎么验证 |
|---|---|---|
| 蓝牙无法连接 | 电量、配对状态、目标设备、连接被其他主机占用 | 音频实际可播放，连接状态稳定 |
| 可以播放但没有近距离弹窗 | 产品是否支持相应广播、当前配置、手机配对状态 | 正常开盖靠近手机时实际出现弹窗 |
| 弹窗有，但设置页图片或电量空白 | 系统识别缓存、上报字段是否完整且一致 | 重新连接或必要时重新配对后检查图像与电量 |
| 型号/序列号 Unknown | 设备是否已有这些字段、上报是否被关闭、运行缓存是否刷新 | 系统关于页面实际显示设备原有字段 |
| 控件存在但灰色 | 佩戴和连接状态、盒子状态、系统与伴侣 App 使用的控制路径 | 控件可操作，且真实硬件行为同步变化 |
| 高级功能入口出现 | 对应硬件、协议数据及实际功能是否存在 | 用功能本身验证，不能仅检查入口 |

## 2. 建立设备与固件范围

记录芯片家族、SDK 字符串、编译目标、编译时间、手机系统版本和连接方式。设备名称和芯片名称都不足以唯一识别固件。

相同外壳或芯片可能配有不同固件、配置布局和充电盒控制器。旧项目中的地址、口令或写入值，不能因名称相似就直接复用。若需读取设备信息，优先采用厂商公开的只读接口；定向连接明确授权的设备，不枚举或操作旁人的耳机。

设备唯一标识、原始日志和备份只在本地保存。公开讨论可使用 `<DEVICE_NAME>`、`<LOCAL_DEVICE_ID>` 等占位符；这些占位符不能直接作为实际命令参数。

## 3. 先排除连接与系统缓存

确保耳机有电并连接到目标手机；必要时暂时断开其他主机。按照目标功能的厂商说明，满足佩戴、开盖等条件，再重新进入设置页。

重新连接后仍然缺图或识别异常，且设备上报配置已经核对正确时，可以将“忽略设备并重新配对”作为下一步。这会删除当前配对记录，不能不加区分地用于所有问题，也不等同于恢复耳机出厂设置。

不要把本机 SDP 查询结果当作另一台手机 UI 的唯一依据。不同系统的缓存、连接角色和查询时机会造成观察差异。

## 4. 需要协议研究时，先取得证据

只有当前面步骤不足以解释问题时，才进入协议分析：

1. 从原始研究仓库或厂商 SDK 核对报文格式，区分请求、响应和异步通知。
2. 先查询当前固件身份、目标参数和可用的双耳转发目标。
3. 如果合法取得了本设备的离线备份，在本地校验大小、哈希和结构，再定位参数的读取与写入代码。
4. 同时检查 setter、getter、调用条件和运行缓存。旧 setter 写入的值可能已经不满足当前 getter 的判断。
5. 为假设写出可证伪的预测。例如：“如果是上报总开关阻断，那么打开开关并刷新缓存后，原有型号与序列号应同时出现。”

本仓库没有分发固件或提供获取第三方受保护内容的下载方法。读取和逆向行为的权利基础需要单独评估。

## 5. 任何配置修改都需要完整闭环

可复用的是下面的流程，不是某个固定字节值：

```text
核对固件身份与适用范围
→ 读取两耳当前值
→ 确认当前值和目标值都在已经研究的范围内
→ 保存修改前记录及恢复方法
→ 只修改必要字段
→ 检查对应命令的真实成功响应
→ 重新读取并比较
→ 检查必要的运行缓存
→ 回到手机验证原始症状
```

任一步失败都应停止依赖它的后续操作。两耳和多个字段的修改通常不是原子事务；必须记录部分完成状态，不能把“某个命令成功”当作整副耳机完成。

已经达到目标值时不重复写入。遇到未知原值、不同构建版本、缺失另一耳、异常响应长度或不稳定缓存时，不猜值、不扩大写入范围。

## 6. 单独验证两耳和真实效果

“当前连接耳”和“另一耳”是动态角色，不是固定左右标签。协议支持转发时，使用设备实际发现的目标，并核对内层响应；外层转发确认不是内层写入成功。

验证系统设置时，分别检查图像、左右耳电量、充电盒电量、型号和原有序列号。序列号只在本地比较，不要复制到公开报告。

噪声控制、自动入耳检测、充电盒声音等，还需测试操作后硬件是否改变。空间音频、心率和查找等入口尤其不能仅凭页面出现就宣称支持。

## 7. 如何记录结论

每个结论明确标注证据层级：

- **观察事实**：设备响应、读回值、用户实测或清晰的 UI 现象。
- **固件解释**：在某个已识别构建中找到的条件判断和调用关系。
- **推测**：与观察一致，但尚未排除其他原因的解释。
- **未知**：没有实测或没有足够资料的问题。

不要把一个成功样本写成“全系列适用”，也不要把失败方案、灰色开关或尚未验证的回退过程写成已解决。
