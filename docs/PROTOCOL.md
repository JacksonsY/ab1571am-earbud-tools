# 协议研究笔记

这些笔记描述本案例与公开 RACE 实现之间可核对的接口事实。它们不是完整厂商规范，也不保证任意设备都开放相同接口。

## 报文与响应

公开 RACE 实现使用包含 head、type、length、command 的小端报文头。普通请求中 length 包含 command 的字节，响应和异步通知也使用不同的 type。[原研究实现](https://github.com/auracast-research/race-toolkit/blob/main/librace/packets.py)

| 本次研究的命令 | 用途 | 必须注意的区别 |
|---|---|---|
| `0x0301` | SDK 信息 | 当前样本返回的首个内容字节与字符串长度相关，不能按通用状态码解释 |
| `0x1E08` | 构建信息 | 按该命令实际布局解析平台、SDK 和时间 |
| `0x0A00` | 读取 NVKEY | 当前样本有独立的长度字段，不能套用写入响应的布局 |
| `0x0A01` | 写入 NVKEY | 当前样本须检查成功状态，并另行读回目标值 |
| `0x0D00` | 发现转发目标 | 依据实际返回选择另一耳，不能固定写死角色 |
| `0x0D01` | 转发内层命令 | 外层确认与内层命令结果不同，必须校验内层响应 |

通用接收器需要处理分片和一条通知中的多个完整帧，并验证长度、命令号、响应类型和超时。不匹配的消息不能当作当前命令的成功响应。

## 两耳链路

本次使用设备发现的 AWS 转发目标读取另一耳。另一耳一度不可达，之后角色及链路状态发生变化才恢复。即使两耳都戴着，也不能假定转发链路已经建立。

旧 SDK 中出现的某些回退目标不被本次固件支持。公开协议示例可以帮助理解格式，但不能代替对当前固件分派路径的确认。

## 配置、缓存和 UI 是三层状态

```text
持久配置
    ↓ 固件启动或更新逻辑
运行缓存 / 当前角色状态
    ↓ 广播、设备信息或控制协议
主机识别状态与系统 UI
```

只验证第一层不足以证明第三层已改变。本案例同时遇到了旧口令写值与 getter 判断不一致、DeviceInfo 上报总开关关闭，以及手机重新配对后恢复图片的情况。

若必须操作缓存，需先证明地址属于该构建、数据已加载、读值稳定、写入宽度正确且邻接字段可完整保留；无法满足时应停止。本仓库不公开可直接执行的 RAM 写入配方。

## 建议的验证记录

每项操作在本地记录：固件范围、连接角色、参数编号、旧值、目标值、响应验证、读回验证、真实 UI/硬件结果，以及是否只完成了部分步骤。公开时仅保留非个人字段和结果摘要。

固件镜像、配置区和完整蓝牙包可能包含设备身份或密钥；即使只想公开一个参数，也应采用字段白名单重新生成摘要，而不是上传整个原文件后依赖读者忽略其他字节。
