AB1571AM 耳机
互操作性排查记录

从弹窗、图片到设备信息上报：沿着报文、配置条件与运行状态，追踪一次兼容性问题的完整分析过程。

研究日期：2026-10-05范围：一副设备 / 一个构建验证环境：macOS + iOS 27.0.1

摘要

这次排查面对的并不是一个单独的“弹窗开关”：最初是弹窗不出现，随后是系统设置页图片空白，最后是型号和序列号显示为 Unknown。它们发生在不同环节，需要用不同证据解释。

本案例通过 BLE/RACE 定向查询、固件静态分析、双耳配置核对和手机端观察，恢复了弹窗、图片及设备原有信息的上报。充电盒声音在伴侣 App 中可控，但 iOS 开关仍灰，原因尚未确定。

本文解释原理与分析方法。文中的参数关系仅对应下列固件，不能当作其他设备的通用写入清单；界面恢复也不代表获得官方认证或具备全部原装功能。

01 / INVESTIGATION METHOD

先把“没有正常显示”拆成不同问题

同一张设置页面会混合呈现多个来源的数据。设备可能已经保存了正确参数，却仍在使用旧的运行缓存；也可能已经正确上报，但手机保留着先前的识别状态。看到最终页面异常，不能直接推断是哪一个参数有问题。

这里把固件的非易失配置存储称作 NVDM，把运行时供代码直接读取的副本称作缓存。NVKEY 是配置项的编号；知道编号之后，仍要确定它的值域、读取方式和使用条件。

建立两种验证闭环

协议闭环回答“命令是否按预期执行”：识别固件、读取原值、记录变更、检查对应响应、再次读回。用户端闭环回答“最初的问题是否消失”：回到手机检查弹窗、图片和设备信息，并在涉及控制时测试硬件行为。

两种闭环缺一不可。蓝牙连接成功，只能证明链路建立；收到转发确认，只能证明某层接收了请求；参数读回正确，也不能代替手机端验证。

实机观察

直接响应、读回值或设备所有者实际确认的结果。

固件解释

在指定构建的代码路径中找到的条件与调用关系。

推测 / 未知

与现象一致，但尚不足以确定根因或证明能力的部分。

原始固件、配置区备份、设备标识和截图保留在本地。公开材料提供脱敏结论与配套代码，因此读者无法仅凭本页面完整重放全部实机证据。

02 / TRANSPORT & FRAMING

找到能通信的路径，再确认每个字节的含义

为什么 Mac 可以直接完成查询

本样本同时暴露了经典蓝牙服务和 BLE 服务。经典蓝牙侧能发现 Airoha_APP 及 RFCOMM 端点，但实际打开通道返回错误；BLE 侧则成功发现 RACE 的写入与通知特征，并返回 SDK 和构建信息。

BLE 提供传输通道，RACE 规定本次维护通道中的命令格式。Mac 通过它查询和调整耳机内部状态；随后影响手机界面的，是耳机自己的广播、信息上报和手机识别流程。RACE 查询本身不是手机弹窗的绘制命令。

实机观察

最终查询与受限修改通过 Mac 的 CoreBluetooth 完成，没有依赖安卓 USB 调试。这个结果说明本样本的 BLE 路径可用，不说明所有 Airoha 固件都开放相同接口。

“服务被广播出来”和“通道实际可用”是两件事。发现阶段应定向匹配明确授权的设备，然后用响应确认链路，不能把附近任意同名设备当作目标。

03 / A SETTER–GETTER MISMATCH

弹窗：为什么旧口令存在，却没有生效

公开讨论容易把“发送某个口令”当作答案，但口令只是进入固件函数的一种入口。真正决定结果的是：它写入什么值，当前代码又如何读取和判断这个值。

从字符串追到实际条件

  1. 定位线索。从合法取得的固件中找到旧功能名或口令字符串；文字存在只是线索，尚不能证明对应路径可达。
  2. 追踪调用。沿字符串引用找到命令处理与动作分派，再追到实际写入配置的函数。
  3. 核对读取。反向寻找这些配置项的 getter 及其调用者，比较“写入什么”和“什么值会被识别为有效”。
  4. 回到设备验证。先读取原值，在明确范围内变更，检查两耳读回，再观察手机是否出现预期弹窗。

在本构建中仍能找到旧版弹窗口令对应的处理路径。继续追踪后发现，旧路径会把 FC04 写成 01，而当前 getter 识别的是 7A。这就形成了“旧写入约定”和“新读取判断”不一致的情况。

这个判断还与 FB03 的值共同作用。下面只保留本案例相关的逻辑，用伪代码表示；它不是可执行的补丁。

if FC04 != 0x7A:
    popup_condition = false
else if FB03 == 0:
    popup_condition = true
else if FB03 == 1:
    popup_condition = false
else if FB03 == 2:
    popup_condition = another_runtime_condition

FB03 = 2 还依赖其他运行条件，不能简单称为“开启”。本次也没有使用这个分支来实现修复。

结果与边界

04 / TWO EARBUDS, TWO RESULTS

双耳：转发成功，不等于另一耳执行成功

一副 TWS 耳机存在两个物理端点，但当前连接耳与另一耳的通信角色会变化。因此，重复查询当前连接角色，并不能独立证明两只耳机都完成了修改。

先发现目标，再校验内层响应

本案例先通过 0x0D00 发现可用转发目标，再通过 0x0D01 包装完整的内层 RACE 请求。目标来自设备当时的返回，不是根据旧 SDK 或另一副设备固定填写。

当前实现只把符合预期封装、目标和内层响应类型的帧交给后续处理，避免将外层确认误当成写入成功。[1]

一次不可达，暴露出角色与链路问题

排查过程中，另一耳曾无法通过目标发现取得。之后链路恢复，连接角色也发生变化，才完成相应的核对。即使两耳都戴着，也不能假定内部转发链路已经满足条件。

旧 SDK 中出现过的备用目标并不被本构建支持。正确的下一步是记录当时状态、恢复可验证的链路，再继续读取；随意填写备用目标只会绕过证据，而不会补上证据。

为什么要记录部分完成状态

双耳、多字段的修改不是一个原子事务。若第三步失败，前两步可能已经完成。后续必须依据每项原值、响应和读回决定从哪里继续，不能把整组任务笼统写成“成功”或“完全没改”。

05 / HOST RECOGNITION

图片空白：参数正确之后，还要观察手机

弹窗出现后，系统设置页顶部一度仍没有耳机和充电盒图片，同时有识别信息与菜单表现异常。如果继续把所有现象都归因于耳机配置，就容易在已经正确的参数上反复修改。

这一阶段改变了什么

  1. 核对设备端。先确认两耳相关配置已达到预期，而不是立刻增加新的写入。
  2. 刷新手机识别。断开 Mac，在手机忽略该设备并重新配对。
  3. 回到同一页面观察。耳机、充电盒图片及电量区域恢复显示。

这一步删除并重建的是手机上的配对关系，不等同于耳机恢复出厂。该阶段没有追加 NVKEY 修改，也没有执行 MCU 刷写或软件复位。

可以推断什么，不能推断什么

前后对照支持“手机刷新配对或识别状态与图片恢复有关”。但本次没有读取手机内部缓存，不能宣称已经定位到某个具体缓存字段，也不能保证重新配对可以解决所有缺图问题。

同理，Mac 上一次 SDP 查询的结果不能被当作 iPhone 当前界面的唯一判据。它们是不同主机、不同时间点上的观察，应分别记录，而不是强迫一个探针结果解释全部现象。

06 / DEVICE INFO & RUNTIME CACHE

Unknown：字段已经存在，为何仍不显示

本样本原本已有型号字符串 A3065 和工厂序列号。系统显示 Unknown，不能直接解释为“设备里没有这些值”，也不意味着应该写入一个新序列号。

第一层原因：整组信息上报被挡住

静态分析显示，本构建中的 FB00 会影响 DeviceInfo 发送路径。关闭时，发送函数提前返回，整组设备信息不会沿该路径发出。因此，一个总开关就可以同时影响多个字段的显示。

// 简化后的因果关系，不是完整设备信息协议实现
if device_info_enabled == false:
    return

payload = build_from_existing_device_information()
send_device_info(payload)  // 对应研究中的 0x001D 信息路径

这里的 0x001D 属于固件面向主机的设备信息路径，与前文维护通道中的 RACE/NVKEY 命令不是同一层接口，不能直接互换使用。

这解释了为什么本次处理的是“已有信息的上报”，而不是改写型号、序列号或品牌身份。型号和原序列号保持原样。

第二层原因：持久值与缓存不是同一个位置

更新持久参数后，不能假定正在运行的固件立即重新加载了它。该构建存在已加载状态和 DeviceInfo 开关的运行副本，需要单独核对。

使用字宽写入接口时，修改一个逻辑标志也可能触及同一个对齐字中的相邻字节。本次工具先确认精确固件身份和字段已加载，再两次读取同一个字，确认稳定后只替换目标字节，并比较完整读回。

缓存已经一致时无需重写；未知标志、未加载或读值变化时应停止。这个过程只适用于已确认的构建与位置，不能把固定地址移植到其他固件。

实机结果

两耳的持久 FB00 和运行标志分别核对为开启状态，随后手机重新连接，设备所有者确认型号与原有序列号恢复显示。本次没有公开序列号内容，也没有通过伪造字段实现显示。

07 / AN OPEN QUESTION

充电盒声音：两种控制路径不能直接等同

最后仍存在一个边界明确的未解决项：充电盒本身会响，伴侣 App 可以控制声音，但 iOS 的“启用充电盒声音”保持灰色。

Apple 官方说明原装 Pro 3 支持这个开关，并要求满足佩戴与连接等条件。Apple 社区中的 Pro 2 用户也报告过类似的灰色开关，但这些个案不能用来直接确定本样本的根因。[3][5]

外部协议研究可以提供控制命令线索，但“其他项目记录了一个控制码”不能证明当前固件实现了它。还需要确认具体接收路径、能力协商、状态返回以及盒子侧行为。[4]

当前结论止于这里

硬件声音功能和伴侣 App 的控制路径可用；iOS 原生控制未被本次修复。状态同步和协议适配都仍需进一步区分，本次没有为了让开关变亮而继续猜测参数。

可以迁移的是方法，不是写入值

新设备适配应重新建立固件范围、报文布局、读取与写入条件、双耳行为和恢复依据。相同芯片或相似外壳，都不足以跳过这些步骤。

  1. 为原始症状定义可观察的成功标准。
  2. 先取得只读证据，区分持久配置、缓存、上报与主机状态。
  3. 追踪 getter、setter 和调用者，不只搜索口令或常量。
  4. 仅在明确范围内作最小变更，逐项记录并读回。
  5. 回到真实 UI 和硬件验证，同时保留未验证事项。

本次没有擦除或刷写 MCU，没有恢复出厂，也没有为验证回退流程而撤销已经成功的结果。原始私人材料不随公开页面分发，实机样本数量也不足以形成全系列兼容性保证。

研究和自用不自动构成法律免责。只操作本人合法持有或明确获授权的设备；公开时保护私有标识、密钥和第三方材料。项目的具体发布边界见隐私与法律说明。
