01

研究摘要

Abstract
背景
同一副耳机依次出现弹窗缺失、图片空白及型号/序列号 Unknown。相似的界面异常，可能来自不同的状态层。
方法
结合定向 BLE/RACE 查询、指定构建的静态分析、双耳参数读回、主机重新配对及设备所有者反馈，对候选机制进行交叉核对。
结果
本案例恢复了弹窗、耳机与充电盒图片，以及设备原有信息的上报。充电盒声音可由伴侣 App 控制，iOS 原生开关仍灰。
解释边界
证据支持多个环节共同影响界面的解释，不支持全系列兼容性、原装身份或全部高级功能的推断。研究未实施随机化、独立重复或完整逐项消融。

关键词BLE / RACENVKEY双耳转发运行缓存DeviceInfo

适用范围

本文是一个构建、一个设备对的工程案例。参数、协议解释和修复结果必须与这个范围一起阅读；页面展示的文字和示意图不构成跨固件操作清单。

02

研究问题与假设

Questions
RQ1

旧版功能入口仍然存在时，弹窗为什么可能继续失效？

RQ2

图片、型号和序列号的异常，是否来自同一个状态层？

RQ3

伴侣 App 与系统原生设置，对同一硬件功能的控制是否等价？

以下假设是对排查过程的事后整理，并非预注册实验。每条假设都保留了可检验的预测和当前证据的解释边界。

03

方法与研究设计

Methods

3.1 对象、环境与分析单位

分析单位是一副耳机，而不是两个相互独立的耳机样本。设备的双耳角色可能切换，但这种切换不增加独立样本量。主机使用 macOS；手机系统版本由设备所有者报告为 iOS 27.0.1。

构建时间

这些字段用于界定构建范围，不是完整固件的密码学认证。具有相同芯片名称或版本文本的其他设备，仍需重新核对接口、状态与配置布局。

3.2 将维护通道与呈现通道分开

在本案例中，Mac 通过 BLE 承载的 RACE 命令查询和调整耳机。手机界面则取决于耳机自身的广播、设备信息上报与手机识别行为；RACE 不是直接向手机绘制弹窗的接口。

NVDM 在这里指固件的非易失配置存储；NVKEY 是配置项的编号。运行缓存则是代码在执行时使用的副本，它与持久配置可能暂时不一致。

3.3 通信与响应解析

经典蓝牙侧能发现服务，但 RFCOMM 通道打开失败；BLE 路径成功返回 SDK 和构建信息。这个差异决定了本次采用的通信方式，不应推广为所有固件的能力。E01

3.4 双耳确认与失败处理

先通过 0x0D00 发现当前可用目标，再用 0x0D01 转发完整内层请求。外层转发确认不是另一耳的执行结果；判断成功还需要匹配内层命令、响应语义并重新读回。

另一耳曾不可达，随后链路恢复并发生角色变化。记录因此以具体步骤和当时角色为单位，而不是把“连接耳”永久等同于左耳。未知原值、异常响应、缺少 peer 或不稳定缓存都使依赖它们的操作停止。

识别构建记录原值最小变更核对响应分别读回主机端验证

这是一组顺序检查，不是原子事务。失败前的步骤可能已经生效，需要明确记录部分完成状态。

05

结果与机制解释

Results
F1

配置入口与读取条件存在版本差异

E02E03

分析从旧功能字符串出发，沿引用追到动作分派、setter，再反向检查 getter 和调用条件。关键不是“找到口令”，而是确认写入约定与读取判定是否一致。

在本次使用的 FB03∈{00,01} 范围内，已分析的局部判定可概括为：

C_local = (FC04 == 0x7A) ∧ (FB03 == 0x00)

这是局部条件的简化表达，不是“手机一定弹窗”的完整模型。FB03=02 还有运行条件，本次没有用它实现修复。

字段本样本原值验证后值
FB030100
FC04017A

读回结果和所有者反馈支持这个组合在本案例中有效。由于缺少完整消融，不能把联合干预进一步解释为每个字段独立效应的实验估计。

F2

图片恢复与主机重新识别相关

E04

在设备参数已核对后，本阶段只刷新手机的配对关系，没有追加配置写入。图片和电量区域随后恢复，说明继续改动耳机字段并不是唯一合理的排查方向。

推断强度

证据与主机缓存或识别刷新有关的解释一致，但尚不能定位某个内部缓存字段。重新配对包含多项状态变化，也不等于耳机恢复出厂。

F3

字段存在与字段上报是不同条件

E05

本样本已包含型号 A3065 和工厂序列号。静态路径显示，FB00 关闭时 DeviceInfo 发送函数提前返回，因而多个字段可以同时显示 Unknown。

// 因果关系示意，不是完整设备协议
if device_info_enabled == false:
    return

payload = existing_device_information()
send_device_info(payload)

持久开关还需要与运行副本分开核对。针对已确认构建的缓存同步采用两次稳定读取，只替换目标标志，并比较完整读回。

手机重新连接后，所有者确认原有信息恢复显示。这支持上报门控与运行状态的联合解释；本次没有生成、复制或替换序列号。

F4

原生充电盒声音控制仍未解决

E06

伴侣 App 的控制有效，只证明一条控制路径可用。iOS 设置可能依赖不同的能力、状态和协议交互，不能由前者推出后者已经适配。

原装产品说明和外部协议项目提供对照线索，但不能替代目标固件的独立验证。本案例尚未确定灰色开关的具体根因。[4][3]

06

讨论与有效性威胁

Discussion
L1

外部有效性：仅有一个设备对

没有跨厂商、跨固件或跨系统版本的独立重复。芯片名称一致不能代替构建、协议和配置的匹配验证。

L2

因果归因：存在联合干预

弹窗涉及多个配置字段，设备信息涉及持久值与缓存，重新配对也改变了多项主机状态。当前证据不足以分别量化这些因素的独立贡献。

L3

测量边界：部分结果来自用户端观察

没有独立采集手机内部缓存，也没有通过完整通讯抓包复核每一个信息包。静态解释、读回和界面观察应保持区分。

L4

构念边界：界面不代表能力或身份

弹窗、图片、字段和功能入口不能证明官方认证。真实心率、精确查找及全部高级功能没有在本案例逐项验证。

L5

报告与复现：原始私人材料未公开

公开源码和摘要可以支持部分复核，但不能让读者仅凭仓库完整重放固件静态分析与实机过程。

研究结论

将配置、运行状态、对外上报和主机识别分别取证，比用单个“开启口令”解释全部现象更符合本案例。可以推广的是分层核对方法；具体字段、地址和有效值仍需在新设备上重新建立证据。

复现与材料可用性

Reproducibility

应区分三件事：复跑公开工具的离线检查、核对一个新设备的只读行为，以及复现原始实机结果。它们需要不同的材料和授权，完成第一项不代表后两项已经完成。

从公开材料开始

  1. 阅读固件范围与工具说明，确认主机要求和保护条件。
  2. 在本地复跑合成测试，记录实际执行的版本和结果。
  3. 有明确设备访问授权时，再建立定向只读证据。
  4. 适配新构建时保留独立 profile、原值检查与读回保护，最后进行真实 UI 和硬件验证。

实机证据来自研究过程中的本地工具；公开版本经过脱敏、构建与离线检查。不要把历史案例结果写成公开二进制已经完成多设备认证。
